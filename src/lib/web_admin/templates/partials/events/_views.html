{# ================================================================ Events — the part every view of both sub-sections shares. The section holds two different things and each one has its own registry below. RULES are configuration: "when this happens, tell these people". The table lists them and answers "what is configured", and leaves two questions it cannot: * which rules reach a given CHANNEL. If Telegram breaks, what stops arriving? The channel column shows icons per row, so the answer is a scan; grouped by channel it is a count. The same view is where a rule with NO channel shows up — a rule that matches perfectly and notifies nobody, which nothing else on the page makes obvious. * whether a rule ever actually fires. `last_fired` is a column you can sort by; what you want is the triage — failing NOW, never fired at all, or delivering. A rule that has never fired is either a gap in the alerting or dead configuration, and both are worth knowing about before the incident, not after. The LOG is history: one line per notification sent. Beyond reading it as a log (the timeline), the two questions are per-rule ("which rule is noisy, which one is failing") and per-channel ("has email been failing since 10:00?"). Both are things the flat list contains and never states. The summaries describe the whole filtered set, not the page, and draw no pagination — the same rule the Audit views follow, for the same reason: page 2 of a summary is not a thing. What must not differ is what a RULE is: the channel vocabulary, the delivery verdict and — the part that is not cosmetic — the action buttons.
