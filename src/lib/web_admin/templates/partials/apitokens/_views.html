{# ================================================================ API tokens (administration) — the view registry. The table answers "what standing access exists" a row at a time, which is the right shape for acting on one of them. It answers two other questions badly, and they are the questions an access review is actually asking: • **By account** — whose automation is this? A person leaves and what has to be cut is everything their name owns, and the table only shows that if you sort by the right column and count the rows yourself. The grouped view puts the account in the subject position and the count beside it, which is the same information arranged as the question. • **By permission** — who can write configuration without signing in? That is the question a review opens with, and no ordering of the table answers it: a token's permissions are a LIST inside a cell, so the flag you are looking for is scattered across rows. Inverting it — a block per permission, the tokens that carry it underneath — is the only shape in which "nobody should still have this" is a thing you can see. Both grouped views are `summary` mode: they are handed every row the filters left standing rather than the page on screen, because a count over one page is a statement about the pagination ("3 tokens can edit users" when there are ten, and a different three next page). THE SHAPE IS A RAIL, not a stack of cards. The first version drew one card per group down the page, which put the answer to "how many groups are there" above the fold and the answer to "what is in this one" three screens down — and made every group compete for the same width. The panel already owns this shape: an index down the side and the open thing beside it, filling everything left, is what Configuration and Modules do.
