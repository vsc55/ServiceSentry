{# ================================================================ Infrastructure — "how is this machine", before the other thousand values. A device with a full set of SNMP profiles answers around a thousand measurements. The Measures tab is right for that — a rail of families, a table per family — and it is the wrong screen for the question somebody actually opens a device with: is this box all right, how hard is it working, is it running out of room. WHICH VALUES THOSE ARE IS NOT DECIDED HERE. The profile declares them (`"headline": true`), because it is a fact about the equipment and not about the panel: a NAS answers with its system status and its temperature, a switch's headline is throughput, a UPS's is its battery and its runtime. A core that picked them by field name would be a core that knows what a NAS is — and would have nothing to say about the next kind of device somebody adds. So this file draws whatever was flagged, in whatever units it came in, and a device whose profiles flag nothing gets told that plainly rather than being given an empty box. ================================================================ #} /** The headline figures, as tiles — the device's own first, then per row. * * Two shapes because there are two kinds of answer. "CPU idle 87 %" is about the box; "used * 412 GB of 3.6 TB" is about one filesystem, and there are usually several. Drawing the * second kind as loose tiles would be twelve numbers with no way to tell which volume each * belongs to. */ function _infraDetailsPane(metrics) { const flagged = (metrics || []).filter(m => m.headline); if (!flagged.length) return `

`; const own = flagged.filter(m => !m.row); const rows = new Map(); for (const m of flagged.filter(m => m.row)) { const k = `${m.row_group || ''}\u0000${m.row}`; if (!rows.has(k)) rows.set(k, {row: m.row, group: m.row_group || '', items: []}); rows.get(k).items.push(m); } // Rows in a stable order. ${own.map(_infraDetailTile).join('')}

${esc(sec.label)}
` : ''}
${sec.rows.map(_infraDetailRow).join('')}
`).join('')}`; } /** One figure, big enough to read from across the room. * * The value is drawn by the SAME code the Measures tab uses (`_infraValueHtml`): a state is a * badge with the word the MIB gives it, a byte count is scaled to something a person reads, * a percentage gets its bar. ${esc(m.label || m.field)}
${_infraValueHtml(m)}
${esc( m.source_short || _infraShortLabel(m.source_label || ''))}
`; } /** Where a figure came from, for the hover: the part of the device, then the check. */ function _infraTileTitle(m) { return [m.source_label || '', m.item || '', m.module || ''].filter(Boolean).join(' · '); } /** One row of the device — a store, a filesystem — with its figures beside its name. * * A row whose profile declared BOTH halves of a proportion is drawn as one: HOST-RESOURCES- * MIB reports every store the same way, memory and mounted volume alike, as a size and an * amount used — and two byte counts side by side is arithmetic left to the reader when the * answer they want is "83 %". It used to be pinned at a // 14rem basis, so a disk with two readings stacked them and the card grew downwards — a // shelf of eight disks became a column of tall boxes with an empty right half each. // `flex: 0 1 auto` lets the readings sit side by side and lets the whole card wrap when the // pane genuinely runs out of room, which is the thing that should wrap. return `

${esc(m.label || m.field)}
${_infraCardValueHtml(m)}
`).join('')}
`; } /** A reading on a summary card: the same value, with a state drawn as a MARK. * * Everywhere else a state is the word the MIB gives it, which is right — "Initialized" and * "Not initialized" are two different pieces of news and only the word separates them. What counts as "too full" is a decision about the installation and * the panel has not been given one — the same reason the percentage bar beside it is grey. * Inventing 80 % here would be the screen turning something amber on its own authority. */ function _infraDonut(used, total, free) { // A table reports whichever half it has: HOST-RESOURCES gives an amount USED, and // SYNOLOGY-RAID-MIB gives the space FREE. ${esc(m.label || m.field)}
${_infraValueHtml(m)}

${esc(used.label || used.field)}
${_infraValueHtml(used)}
${esc(total.label || total.field)}
${_infraValueHtml(total)}
`; } // Whole percent in the ring: "10.42 %" inside a 52px circle is a number nobody reads, and // the exact figures are right underneath it. ${esc(fu.value)} ${esc(fu.unit)}
${esc('/ ' + ft.value + ' ' + ft.unit)}
${free ? `
${esc(_fmtMeasure(Number(free.value), free.unit).value)} ${esc(_fmtMeasure(Number(free.value), free.unit).unit)} ${esc(t('infra_free'))}
` : ''}
`; } /** Everything the device says about ONE row, wherever it said it. * * A row is a name the equipment chose, and several profiles can be about the same one: a disk * is a row of SYNOLOGY-DISK-MIB (its model, its temperature, its health) AND the group that * eighty rows of SYNOLOGY-SMART-MIB belong to (`row_group`, split from "Drive 1 / Reallocated * Sector Count" by the pattern that table declares). So the match is on either, and what * comes back is the disk's whole story rather than the profile that happened to be open. */ //: The identity facts that are a NAME for a row rather than a description of it. A model or a //: kind is shared by every disk in the box; a bay, a serial or a name is one row's alone. const _INFRA_ID_ROLES = new Set(['bay', 'serial', 'name', 'id', 'wwn']); //: alias → row_key, for the aliases that belong to exactly one row. Rebuilt with the facts. let _infraRowAlias = new Map(); /** Work out every name this device uses for each of its rows. * * Two tables of one device index it by different columns, and there is no rule that says they * agree: SYNOLOGY-DISK-MIB names a disk by `diskName` ("Drive 1") and files its `diskID` * ("Disk 1") beside it, while SYNOLOGY-SMART-MIB names its rows by a column of its own. So * the SMART rows of a disk grouped under a name the disk's own row never had, and clicking * the disk showed its six readings and none of its eighty attributes. * * Built from what the device SAID — the identity facts it reported for each row — and never * from a rule about how the names look. But SYNOLOGY-SMART-MIB also reports the serial of the // disk each of its rows belongs to, and so does the disk table: same physical object, same // number, no convention. Any identifying fact does — the rule is "these two rows are about // the same thing because the device gave them the same name for it". const owner = new Map(); // `role\u0000value` → row_key for (const list of _infraRowFacts.values()) for (const a of list) if (_INFRA_ID_ROLES.has(a.key) && !nestedOf.has(a.row)) { const k = `${a.key}\u0000${a.value}`; if (!owner.has(k)) owner.set(k, new Set()); owner.get(k).add(a.row); } for (const list of _infraRowFacts.values()) for (const a of list) { const group = nestedOf.get(a.row); if (!group || !_INFRA_ID_ROLES.has(a.key)) continue; const owners = owner.get(`${a.key}\u0000${a.value}`); if (owners && owners.size === 1) claim(group, [...owners][0]); } _infraRowAlias = new Map(); for (const [alias, keys] of claims) // Claimed by exactly one row, AND not already the name of a row itself. The second // half is the one that bites: with an expansion unit the shelf disk's split name is // "Drive 3", which is the internal disk's whole name — one claimant, and completely // the wrong disk. A name that already belongs to a row is never a nickname for // another. if (keys.size === 1 && !rowKeys.has(alias)) _infraRowAlias.set(alias, [...keys][0]); } /** Everything the device says about ONE row, wherever it said it. */ function _infraRowDetail(key) { const name = String(key || ''); if (!name) return []; const all = (_infraDetail && _infraDetail.metrics) || []; // Matched on `row_key` — the name the DEVICE composed, before the profile's split — and // never on the split half. Looking them up by the split name puts them // back together, which is the bug that split was written to fix. // // A nested row's group is matched through the alias table, because the table it came from // may index the device by a different column than the row's own table does. return all.filter(m => m.row_key === name || m.row_group === name || (m.row_group && _infraRowAlias.get(m.row_group) === name)); } /** How much of it is NOT already on the card. A chevron on a row that opens onto the two * numbers already in front of you is a promise the dialog does not keep. */ function _infraRowDetailCount(row) { return _infraRowDetail(row).filter(m => !m.headline).length; } /** That story, as a dialog: what the row is, what it says now, and everything behind it. * * Two panes, because a disk answers two different kinds of thing and one list of ninety rows * buries the six that matter. The first is the disk itself — health, temperature, life — and * the second is its SMART table, which is eighty attributes each with four numbers and is a * TABLE, not a list: "Reallocated Sector Count 100 100 5 0" is one line, and four lines * saying "Reallocated Sector Count — Valor actual" is the same data made unreadable. * * Bootstrap's own tabs inside the body, so nothing here needs a handler: the dialog is * disposable markup and a tab that needed wiring would need unwiring too. */ function _infraOpenRow(key) { const items = _infraRowDetail(key); if (!items.length) return; // The dialog is titled with what the device calls it, split included: "Drive 3" in the // shelf and "Drive 3" in the box are two dialogs and have to look like it. const own = items.find(m => m.row_key === key) || items[0]; const row = own.row_group ? `${own.row} (${own.row_group})` : (own.row || key); const mine = items.filter(m => m.row_key === key); const nested = items.filter(m => m.row_key !== key); const facts = _infraRowFactsHtml(key); const body = nested.length ? `${facts}
${_infraRowList(mine, key)}
${_infraNestedTable(nested)}
` : facts + _infraRowList(mine, key); showHtmlModal(String(row), body, 'primary'); } /** What the nested rows are called — the profile's own name for them ("SMART"), not ours. */ function _infraNestedLabel(nested) { const m = nested[0] || {}; return m.source_short || _infraShortLabel(m.source_label || m.source || ''); } /** The nested rows, keyed by the name the device gave each one. */ function _infraNestedRows(nested) { const rows = new Map(); for (const m of nested) { const k = m.row || m.row_key; if (!rows.has(k)) rows.set(k, []); rows.get(k).push(m); } return rows; } /** One line per attribute, one column per reading. * * A SMART attribute is a name and four numbers — current, worst, threshold, raw — and it is * read ACROSS: "is the current value near the threshold" is the whole question, and it cannot * be asked of four separate lines. The columns are whatever fields came back, in the order * the profile declared them, so a table with three of them or six works the same. */ function _infraNestedTable(nested) { const rows = _infraNestedRows(nested); const cols = []; for (const m of nested) if (!cols.some(c => c.field === m.field)) cols.push({field: m.field, label: m.label}); return `

`; } /** The row's own readings, one per line. `; }
